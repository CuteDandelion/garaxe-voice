# Voice Lab

Specification-first workspace for an evidence-backed customer-review analysis product. The product turns customer-authorized feedback into a traceable Voice Map: strategic conclusions, recurring themes, exact quotes, and action-ready recommendations.

Start with [docs/product-spec.md](docs/product-spec.md), then read [AGENTS.md](AGENTS.md). No implementation should begin until the readiness conditions in those documents are satisfied.

Validate the documentation baseline with:

```sh
./scripts/check-docs-sync.sh
```

For managed activation, use the redacted [Supabase hosted activation runbook](docs/supabase-hosted-activation-runbook.md). It defines the server/browser environment boundary and a no-network readiness check without containing deployment values.

Overview begins with an exact-once deterministic Signal Story: feedback volume over time, a sortable topic-by-period heatmap, and an adaptive daily/weekly/monthly rating trend only across at least two valid dated buckets on one consistent declared positive source scale, plus source and category context. Known source aliases share one visible group without changing stored provider values. Original rating values are not normalized or inverted; single-period, undated, mixed-scale, or invalid-scale ratings are explicitly insufficient for a trend. Recurrence is not shown. Every chart datum and Voice Map bubble exposes its deterministic value in a tooltip anchored beside the hovered or keyboard-focused mark, flipping within the viewport without obscuring the mark or causing mobile overflow; evidence-cited intelligence and actions follow.

Saved deterministic Overview evidence becomes usable without waiting for the optional intelligence brief. Identical grounded brief requests share one byte-hashed in-flight/completed result; changes to cited evidence, prompt/schema, or model provenance invalidate reuse. Provider failure keeps evidence available and remains retryable.

## Run the MVP

Local Supabase staging is isolated from production. With Docker running and the repository's Supabase CLI available through `npx`, use `./scripts/local-supabase-lifecycle.sh start`, migrate its loopback Postgres, start the API, then run `npm run test:e2e:local-supabase-auth`. `status` reports the owned containers, published API ports, and database/Auth health without printing local keys. Docker may publish the configured ports on all host interfaces; inspect the reported bindings and do not run this development stack on an untrusted network. The ignored `.env` uses only loopback values. After proof, `./scripts/local-supabase-lifecycle.sh stop --confirm voice-lab-local` removes only that project's containers, network, and volumes with `--no-backup`; it refuses any other project ID and verifies cleanup. Use `--dry-run` with any subcommand to inspect its exact scope. Managed Supabase values stay only in Kubernetes configuration/server secrets.

```sh
npm install --cache /tmp/garaxe-npm-cache
npm run dev
```

Quality gates:

The repository also contains CI verification and immutable-image publication workflows under `.github/workflows/`. Deployment manifests and the operator runbook live under `deploy/`; the public Voice Lab hostname is `https://voicelab.elseform.tech`. The former hostname remains an unadvertised rollback route until the candidate release is verified on the new domain.

The current MVP implements a public editorial Voice Map entry, a bounded same-engine temporary demo with a no-store demo PDF, the responsive authenticated workspace, CSV-only ingestion with explicit mapping preflight and review inventory, immutable versioned analysis runs, exact-span signals, governed interpretation, separate top-level Overview and Voice Map sections, append-only Curation, immutable reports, evidence-backed PDF export, organization-scoped sessions, and a managed-PostgreSQL adapter. Demo and authenticated uploaders use the same CSV mapping contract. Authenticated imports accumulate in the selected project; each new run freezes all current matching feedback while earlier runs, Curation revisions, and reports remain immutable. Additional Demo CSVs append only inside the same expiring token-scoped project and create a new immutable run over that project. A Demo allowance accepts 50 unique comments; accepting the 50th closes that project to uploads for an eight-hour cooldown, duplicate retries consume no capacity, and the upload area counts down to a server-confirmed fresh Demo project at the exact reset boundary. While the server still reports an accepted run as active, the browser keeps its honest in-progress state instead of inventing a client timeout.

Performance acceptance is measured per cold/warm stage and workload rather than as one blended number. The current contract records p50/p95 for CSV acknowledgement/persistence, queue wait, first grounded evidence, full completion, saved Overview/Voice Map readiness, and date-range projection. Upload acknowledgement must remain at or below 2 seconds p95; saved-result Overview, Voice Map, and date projection at or below 1 second p95; a 50-record run targets first usable grounded evidence within 10 seconds while full intelligence timing is reported separately. A timing sample fails if exact evidence IDs/counts/links, grounded intelligence input/model/prompt versions, validation, tenant isolation, or security results differ. The date gate additionally requires zero new analysis runs and zero LLM jobs. Provider-capacity targets may be revised only from recorded measurements, never by silently weakening evidence or intelligence.

Local staging may expose `#diagnostics` only when both the development build flag and the loopback API flag are enabled. The owner/admin-only page polls sanitized run, queue, model-call, fairness, CPU, and memory measurements every two seconds without feedback text, prompts, credentials, or reviewer PII. Its focused full-width surface renders real sampled queue/worker, CPU, and memory timelines, active-job and recent-run rows, and only start-time-proven three-user fairness cohorts; unavailable measurements have explicit empty states. **Pause updates** freezes only that browser snapshot for inspection; analysis and queue work continue unchanged until **Resume updates** fetches a fresh snapshot. Production builds omit the page and production API requests receive `404`; this local surface is benchmark evidence, not a production telemetry exporter.

Every retained comment has one canonical persisted outcome at `review_signals.attributes.canonicalOutcome`; legacy `emergingInterpretation` and taxonomy-v1 values remain read-compatible for stored data only. New runs use `semantic-taxonomy-v2-v22`: exactly `pain`, `desired_outcome`, `objection`, `emotion`, or `other`, with bounded topic/label and exact evidence. An explicit request or wanted result is `desired_outcome` even when a current failure motivates it; concrete friction described as frustrating remains `pain` unless the customer's own affect is the main signal. `other` keeps a bounded proposed-type label but never creates a public type. Sentiment (`positive`, `neutral`, or `negative`) is orthogonal metadata, never a semantic category or recurrence state: praise with a stated achieved value is `desired_outcome + positive`; generic affective praise is `emotion + positive`. Legacy `operational_issue` projects as pain when read; historical `feature_request`, `purchase_trigger`, and `praise` remain historical compatibility values. Recurrence remains server-owned (`recurring` or `emerging`), as do grouping, counts, ranking, readiness, and projection. New reports snapshot v2 outcomes; existing immutable snapshots are never rewritten. A run cannot publish a new map until every retained valid comment has a canonical outcome; bounded retry and failed-batch-only split remain unchanged.

Distinct source records remain valid feedback even when their text is identical or nearly paraphrased: each is retained and categorized, while exact/hash/near-similarity groups remain diagnostics and may guide analytical merging. Import rejects a repeated external source ID; normalized-text deduplication applies only when no source ID exists. Demo records likewise receive record-specific canonical hashes so repeated wording cannot silently collapse separate submitted rows.

CSV is the sole customer-feedback ingestion format in Demo and authenticated workspaces. The shared preflight auto-detects documented aliases, requires feedback ID/source/comment text, requires every column to be mapped or explicitly excluded, previews rows, and blocks processing until validation passes. Date, rating plus rating scale, author/customer/context metadata, title, language, reply, entity, and HTTPS source URL are optional but validated when mapped. Workbook, JSON, and arbitrary pasted-comment entry are rejected before queue creation. Requests remain tenant-authorized; parsing is capped at 10,000 rows, 100 columns, and 10,000 characters per cell/comment; stored markup remains literal text in React and escaped PDF output. Public Demo starts retain per-client/global admission, and authenticated imports/analyses retain the organization active-job cap.

Curation is a touch-up workspace, not a manual first-pass sorter. It opens on the grouped engine proposals with one primary action: review a bucket. Accepted or edited buckets use settled-state copy rather than repeating the pending action. Rename and evidence-level correction live inside that selected bucket; combine and custom-bucket actions appear only in the same context. Creating a custom bucket may reassign any retained run-scoped comment from its current machine or curated bucket; the projection removes it from the prior bucket so coverage remains exact-once. Authenticated decisions persist as reversible revisions, with **Undo latest change** placed contextually in Activity; restore recomputes the effective target revision without leaking superseded edit actions into the restored projection. Demo decisions are token-scoped and expire with the isolated demo tenant. The broader audited API action set remains available without turning the first-use surface into a management toolbar.

Top evidence buckets renders the ten highest-support outcomes, ordered by count descending with stable `themeId` ties. Each category panel independently selects its highest-support matching outcome using the same count-descending, stable-`themeId` ordering. Category cards use category-specific empty copy instead of validation-error language. The public header and footer link to Product, Examples, Resources, and About sections on one editorial homepage; section hashes never mount separate marketing routes. Log in and Try the demo remain direct actions. Pricing is intentionally absent until the product decision is governed. All public links retain the governed theme and focus treatment.

Semantic QA has two separate live gates. `test:e2e:*:categories` uses eight controlled comments, two per required actionable category, and requires exact supporting IDs/counts with no category substitution; its earlier 2026-08-11 live Demo and authenticated runs passed 8/8. `test:e2e:*:held-out` uses 20 paraphrased, username-stripped public issue reports with a human category/topic/grouping rubric. D-090's prompt-v21 regression, full automated suite, and the fresh guided-setup recurrence pass, but the 30-comment controlled Demo oracle stopped after exact-once/evidence success because migration-risk comments controlled-09/10 shared one recurring bucket while controlled-11 remained separate. Authenticated, held-out, category, and browser parity lanes were not run after that hard grouping failure; no semantic-quality completion is claimed.

`test:e2e:public-demo:independent` and `test:e2e:authenticated:independent` use a separate ten-comment consent-safe synthetic public-style holdout. Its five topics—food-allergen substitutions, bike-dock reservations, renter energy-monitor permissions, event-ticket transfer confirmation, and museum-audio language scope—are intentionally absent from the blinded-100 topics. A preflight test requires unique IDs/text, two comments per taxonomy-v2 category, no shared topic-group names, no exact text matches, and no normalized four-token shingle overlap with the blinded-100 input. Gold category/topic relations remain outside the submitted input. The fresh Demo and authenticated runs each accounted for all 10 inputs exactly once; the authenticated report snapshot retained exact evidence for 10/10 inputs, and desktop/mobile checks found no page overflow. This is a one-run QA observation, not prompt or engine tuning evidence or a claim of representative customer performance.

`npm run test:e2e:authenticated:blinded-100` is a separate frozen-engine evaluation lane, not a production gate or engine change. It sends one gold-free fixture of 100 English consent-safe synthetic public-style comments through the authenticated path, then scores the result against a separate rubric with a category authored for each comment and 200 reviewed within-family pair judgments. The reviewed production-granularity relation contains 175 merge pairs and 25 same-family-but-separate pairs across 26 bounded merge groups; pain has 21 comments, desired outcome 19, and objection/emotion/other 20 each. It reports exact-once coverage, exact-quote rate, overall/per-category category accuracy and confusion, lexical topic-cue coherence, and pairwise merge precision/recall without a composite score. Wilson intervals are descriptive only: paraphrases reduce the effective independent sample toward 26 merge groups, pair observations are correlated, and one run cannot establish repeatability, multilingual performance, or customer prevalence. The fresh frozen-engine corrected-rubric run achieved 100/100 exact-once coverage and exact quotes, 91/100 category accuracy, 99/100 lexical topic coherence, 64/68 merge precision, and 64/175 merge recall. Four reviewed-separate pairs merged, so this is a failing quality measurement rather than a production pass.
The rejected and reverted v23 pair-contract experiment kept exact-once coverage and exact quotes at 100/100, but the grouping gate did not improve: merge precision remained 64/68 (94.1%) and recall remained 64/175 (36.6%). Four retention-timing/report-scope false merges and 111 missed expected pairs remain, so Demo/authenticated browser gates did not run.
After completion, the lane writes a mode-`0600` ephemeral `/private/tmp/voice-map-blinded-100-diagnostic.json` ledger that joins the external rubric to neutral IDs, source hashes, frozen planner state, validated pair-result hashes, and complete-link outcomes; no gold enters model input and no source text or credential is stored in the ledger.
`npm run test:e2e:authenticated:blinded-100:repeatability` is the no-engine-change repeatability lane. It wraps only the isolated verifier's provider boundary, holds exact pair request bodies in RAM without headers or credentials, and replays only observed reviewed errors three times with the identical raw batch body before clearing the array and closing the `memory://` database. It writes no request capture or analysis result to disk and emits only blind pair IDs, request-context hashes, boolean outcomes, schema validity, response hashes, and latency. The fresh run captured 13 unique batches and 21 wrong original decisions; all 63 replayed decisions were schema-valid, with 15 pairs stable-wrong, three variable, and three stable-correct. No Demo, authenticated workspace, or browser live gate followed.

Local development starts both the web app and API. The public root offers the bounded demo; when the public Supabase URL/publishable-key contract is configured, `Log in` uses Supabase email/password auth and the API verifies the returned bearer JWT. On the first verified login only, the server transactionally creates the matching application profile, one `Personal workspace` owner membership, and one `Default project`; repeat logins reuse them, later memberships remain separate, and unauthenticated requests cannot enter provisioning. Without that contract the browser fails closed unless an explicit `VITE_LOCAL_QA_AUTH_ENABLED=true` local fixture is selected; the Node API rejects the legacy staging access-key route whenever `NODE_ENV=production`. `Join waitlist` stores a validated name, normalized unique email, consent version, and creation time through `POST /api/waitlist`; duplicate submissions return the same generic success and joining creates neither an account nor access. Private monitoring is exposed only through authenticated `GET /api/admin/waitlist`: the verified Supabase claim email must match the provisioned profile email and the normalized server-only `VOICE_LAB_ADMIN_EMAILS` allowlist. It returns a count plus paginated contact/consent/timestamp records; `user_metadata` never grants access and direct `anon`/`authenticated` Data API reads remain denied. Starting the live demo returns an honest unavailable response unless the server-side `OPENCODE_GO_API_KEY`, remaining `OPENCODE_GO_*` endpoint/model settings, and `GARAXE_LLM_*` policy contract are complete; the browser never receives provider credentials. Authenticated local data uses PGlite under `.local/pgdata` unless `DATABASE_URL` selects managed PostgreSQL. Demo always uses the distinct temporary PGlite handle at `GARAXE_DEMO_DB_DIR` (default `.local/demo-pgdata`), never `DATABASE_URL`; both handles run the shared queue worker and Demo keeps its fixed expiry cleanup. Managed PostgreSQL startup opens the pre-migrated pool and never executes DDL. The private Storage adapter uses only the publishable key plus the signed-in user's bearer token, fixed organization/project object paths, and private `voice-lab-uploads` / `voice-lab-reports` buckets. Managed bootstrap is migration-file-only: `000_base_schema.sql` is followed lexically by 001, both existing 002 files, 003, 004, 005, 006, and 007. Migration 007 preserves direct Data API denial while allowing only the verified API subject to provision its exact first-login boundary. Security Advisor retains two expected informational notices for deliberately policy-free deny-all session tables plus the hosted leaked-password-protection warning.

`npm run dev:api` loads the server-only, Git-ignored `.env`; `.env.example` is the committed name/default contract and must never contain a real credential. For a local public-demo run, set `GARAXE_DEMO_DB_DIR=.local/demo-pgdata`; `DATABASE_URL` and `GARAXE_DB_DIR` configure authenticated persistence only. The minimum live OpenCode contract is `OPENCODE_GO_API_KEY`, `OPENCODE_GO_BASE_URL`, `OPENCODE_GO_DEFAULT_MODEL`, `GARAXE_LLM_ENRICHMENT_ENABLED=true`, and every `GARAXE_LLM_REQUEST_*`, `GARAXE_LLM_TOKEN_*`, `GARAXE_LLM_*_CONCURRENCY`, `GARAXE_LLM_MAX_OUTPUT_TOKENS`, and `GARAXE_LLM_DEADLINE_MS` value shown in `.env.example`. `OPENCODE_GO_MAX_COMPLETION_TOKENS` overrides the completion budget for both the configured primary and its one fallback attempt in that process, but the server rejects values above 16,384; a separate process/model route keeps its own configured budget and model-scoped admission bucket. The primary route price inputs make its successful token usage cost-visible; fallback cost remains unverified rather than applying the wrong model price. `OPENCODE_GO_FALLBACK_MODEL` is optional; when present it must differ from the primary model and is used once only after a transient primary failure. Never use a `VITE_` variable for a provider credential.

`POST /api/auth/local-session` remains a loopback-only, non-production API compatibility endpoint for developer recovery. It is never called or rendered by the public login UI and returns 404 in production. All Vitest runs force `GARAXE_DB_DIR=memory://` and cannot truncate `.local/pgdata`.

The legacy staging credential/session route is local QA compatibility only: the browser requires the explicit local-QA flag, and the server returns 404 in production mode. It is never the production login contract.

Normal retained-comment categorization uses compact five-item jobs with completeness validation. A measured ten-item parent truncated while both five-item children succeeded, so ten remains the demo input cap—not the engine batch size. Only an incomplete/invalid five-item batch is recursively split through the existing durable queue (`5 -> 2/3 -> 1`); successful siblings are never repeated. For 1,000 comments, normal categorization is 200 calls. One failed five-item batch recovered by its `2/3` children yields 202 total. One batch fully reduced to singletons occupies nine calls including its parent, or 208 overall when it is the only failed batch. If every five-item batch degraded to singletons, the envelope is 1,800 calls—an operational alarm, not normal capacity.

The engine supplies one evidence-backed taxonomy-v2 category per comment; deterministic code validates structure, allowlists, exact evidence, complete coverage, and publication state without replacing that semantic choice with keyword rules.

The current analysis pipeline is reproducible but not model-free. Deterministic preprocessing freezes dataset membership and exact evidence spans; pinned local ONNX sentiment/embedding work supplies internal diagnostics and provisional themes; and the interpretation path reads explicit primary and optional fallback model IDs from server configuration. A transient primary outage/rate limit gets one immediate fallback attempt; a transient fallback failure requeues the same idempotent job with `Retry-After` or capped jittered backoff. Authentication, model-selection, validation, schema, and local acceptance failures never switch models or back off. Customer recurrence replaces provisional themes with a category-bounded planner over immutable source text and pinned source-text embeddings. Exact normalized source duplicates are deterministic edges; other source-similar pairs are bounded adjudication candidates. Components with at most 16 complete pairs retain every eligible pair; larger components retain only stable mutual top-four eligible neighbors. Model-generated topic, label, aspect, and evidence never decide candidate eligibility. New immutable project runs may reuse project-scoped embeddings plus per-review and fixed-pair decisions only when content hashes and the full pipeline/model/prompt/schema/candidate/routing contract match and every prior included review has complete lineage; otherwise the run performs the full path. A guarded `VOICE_LAB_ASPECT_SEMANTICS_ENABLED=true` candidate additionally retains every exact extracted signal as an independent semantic/Curation unit and reuses only complete exact-compatible aspect lineage from migration 008; absent tables, disabled flag, or incompatible lineage keep the established review-level full path. Reuse never creates a vector-only merge and the existing complete-link projection remains authoritative. Invalid or unavailable semantic output fails the incomplete run; invalid or unavailable optional pair output leaves the pair as separate emerging signals. Run-scoped curation records remain an append-only audit stream, and published views retain immutable machine artifacts and provenance underneath.
