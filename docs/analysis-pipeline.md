# Analysis Pipeline

Status: Implemented local MVP pipeline with explicit paid-beta gates
Last updated: 2026-08-11

## Principle

Analysis is a sequence of versioned transformations. The system never writes a conclusion first and invents supporting evidence afterward.

## MVP phases

1. Configuration: freeze objective, entities, dates, ratings, languages, and options.
2. Dataset assembly: record every included/excluded review and reason.
3. Quality/cleaning: normalize without overwriting original text; record exact/hash/near-similarity groups as diagnostics without excluding valid distinct source records; detect language, spam risk, invalid records, and optional PII redaction.
4. Enrichment: deterministic rating groups, dates, entity dimensions, reply state, keyphrase candidates, sentiment, embeddings.
5. Exact segmentation: split sentence/clause evidence with original-text character offsets.
6. Semantic representation: embed segments with pinned multilingual-e5-small ONNX int8, build polarity-specific mutual-nearest-neighbour graphs, and retain only coherent dataset-derived communities. Weakly connected claims remain explicit outliers.
7. Cluster representation: rank literal phrases with c-TF-IDF/KeyBERT-style scoring while preserving customer wording. Count term support once per independent review, not once per repeated segment, and prefer supported two-to-four-word phrases over isolated context tokens.
8. Evidence validation: minimum support, independence, time/entity diversity, contradictions, overlap, and extraction uncertainty.
9. Metrics: prevalence, rating, trend, entity/language/rating breakdown, severity, reply rate.
10. Voice Map synthesis: generate higher-level conclusions only from validated themes.
11. Human review: approve, reject, edit, merge, split, rename, exclude, and pin.
12. Report snapshot: persist approved output and versions immutably.

## Hybrid compute strategy

Use hashes/rules/local libraries for normalization, import identity deduplication, similarity diagnostics, span integrity, candidate generation, group membership, counts, ranking, readiness, and projection. LLM interpretation produces exactly one validated dominant customer signal per retained comment; deterministic clause siblings remain internal. After canonical completeness, the server may send only capped fixed-ID ambiguous pairs for a same-actionable-topic boolean. The model cannot add members or create a component; accepted pair edges join only when every cross-pair is compatible, while failed or rejected adjudication leaves emerging singletons.

Phase one requires no custom training. `Xenova/multilingual-e5-small` is loaded through Transformers.js/ONNX at the pinned revision recorded in code and uses q8 weights, mean pooling, normalized vectors, and bounded batches. Its preliminary diagnostic mutual-KNN floors remain `0.84` mean and `0.81` weakest-member, with `semantic-diversity-gold-v1` measuring purity, paraphrase recall, coverage, and cross-topic merges. These communities and any historical `keep`/`split` artifacts are internal diagnostics only; they do not gate customer signals or recurrence. A later SetFit classifier remains deferred. Invented labels, generic fallbacks, and synthetic-only promotion are prohibited.

The Bluerose API image prewarms both pinned model revisions into `/opt/garaxe/models` during the image build and starts with remote-model loading disabled. Deployment verification must execute both pipelines with the runtime offline setting, confirm the expected 384-dimensional embedding and a valid sentiment result, and record cold/warm latency and peak RSS separately from image-build availability.

LLM work is queued only after immutable dataset membership exists. Categorization must name fixed existing review IDs and return only `semantic-taxonomy-v2-v22` labels (`pain`, `desired_outcome`, `objection`, `emotion`, or `other`), bounded topic/label, orthogonal sentiment (`positive`, `neutral`, or `negative`), and exact source substrings or offsets that satisfy `quote === original_text.slice(start, end)`. The validator rejects unknown IDs, altered evidence, invalid taxonomy values, cross-tenant references, unsupported conclusions, and schema/version mismatches; it does not replace or reject an allowed evidence-backed category through keyword cues. Accepted results persist as `review_signals.attributes.canonicalOutcome`; Dashboard and Curation read it as their sole per-comment authority, while new reports snapshot it without rewriting existing immutable reports. `emergingInterpretation` and taxonomy-v1 values remain legacy read compatibility. Pair adjudication receives only server-selected fixed pair IDs plus canonical topic/label/quote and returns only `{pairId, sameTopic}`; true requires one named specific operator intervention that addresses both comments, and differing interventions require false. Model output never chooses inclusion, counts, rank, readiness, or broad membership. A terminal structural, evidence, or completeness failure fails the new run; pair-adjudication failure defaults to separation. Category repeatability is an evaluation and prompt-quality gate, not a runtime publication veto.

The routing policy requires an explicit primary model ID and permits one distinct optional fallback model ID from server configuration. Only a classified transient primary outage, timeout, or rate limit may trigger the one immediate fallback attempt; schema, evidence-validation, authentication, missing-model, request, and local acceptance failures fail closed on the configured primary route. Provider/model selection is recorded per attempt and versioned per accepted job result so availability changes do not make a completed run irreproducible.

The deterministic pipeline remains the evidence and reproducibility authority, while validated LLM interpretation is the default vocabulary and narrative shown to curators. If interpretation is disabled, waits beyond its deadline, hits an open circuit, exhausts retries, or dead-letters, the run records the sanitized degraded-mode reason and completes with deterministic presentation. A successful deterministic artifact never implies complete model coverage. Optional monetary budget exhaustion applies only when an administrator explicitly enables verified-price spend enforcement.

After **Run analysis**, the client monitors the immutable run rather than estimating progress locally. The server derives terminal job percentage, outstanding queue and provider-capacity waits, in-flight work, fallback/failure totals, and interpreted-theme coverage from durable queue and theme records. Navigation or reload may reattach to the latest non-terminal run. Progress reaches 100% when every job is terminal; interpretation coverage remains a separate quality measure so a fallback completion cannot be mistaken for successful model intelligence.

### Quota-aware execution

Before a call, the queue consumes one request token plus estimated input/output token capacity from the provider/model buckets and acquires every configured concurrency slot. Workers claim with `FOR UPDATE SKIP LOCKED`, bounded per-organization concurrency, priority, and age-based fairness. Leases require heartbeats and may be reclaimed after expiry. Only providers with an explicitly enabled verified-price policy also reserve hierarchical integer-micro spend.

After the one immediate configured fallback attempt, a transient fallback timeout, `429`, or eligible `5xx` requeues the same idempotent job with provider `Retry-After` when supplied or capped exponential backoff with full jitter. This route creates no extra semantic job and performs no recovery split. Authentication, authorization, invalid-request, safety, validation, and schema-incompatibility failures do not fallback or retry blindly. Attempts remain bounded and terminal failure retains any prior completed map; it does not publish a partial replacement. Repeated provider failures open a provider/model circuit until a timed half-open probe succeeds.

## Confidence

Confidence combines evidence volume, semantic consistency, reviewer independence, time/entity/source diversity, and extraction certainty, with penalties for contradiction, duplication, dominance by one incident, and overlapping themes. User-facing labels: High, Moderate, Emerging, Weak, Insufficient. Semantic diagnostics record cluster mean similarity, weakest-member similarity, ambiguous membership, clustered coverage, and outlier count; volume never overrides a failed coherence gate.

## Implemented run status and stage values

Persisted `status` values are `queued`, `assembling_dataset`, `preprocessing`, `interpreting_clusters`, `completed`, and `failed`.

Persisted `stage` values used by the current runtime are `queued`, `assembling_dataset`, `preprocessing`, `extracting_signals`, `forming_themes`, `interpreting_clusters`, `completed`, and `failed`. Any future cancellation, review, validation, metric, insight, or report-building lifecycle value requires a schema and runtime change before it may be documented as implemented.

After the saved map and effective Curation projection exist, the optional Overview intelligence pass receives only bounded effective-bucket labels/topics/categories/sentiment/summaries and exact review-ID/quote evidence. It returns prose plus known bucket citations under `overview-intelligence-v1`; it has no count, rank, grouping, category, inclusion, or mutation fields. Strict citation/action validation fails closed to a deterministic proof-only Overview.

## Evaluation

Maintain a gold fixture set containing mixed statements, ratings-only, duplicates, multiple languages, negation, sarcasm, named staff, pros/cons fields, long/short text, and contradictory evidence. Score exact-span integrity (required 100%), cluster coherence and analyst agreement, label precision/recall once SetFit exists, unsupported-claim rate (required 0), stability across reruns, and report usefulness. Record cold/warm latency and peak RSS against the 4 vCPU/8 GB budgets. Model/config/pipeline changes require comparative evaluation before rollout.

### Category-first per-comment interpretation

After deterministic evidence persistence, the run enters interpretation. Exactly one dominant customer signal per retained comment receives compact engine interpretation; normal jobs contain up to five comments. The engine returns a validated signal-type set, topic/aspect/label, confidence, review identity, and exact quote. A measured ten-item parent truncated while both five-item children succeeded. Completeness validation requires every requested comment exactly once. Only a failed five-item batch recursively splits through the existing durable queue (`5 -> 2/3 -> 1`); successful batches and siblings are retained. The validator rejects malformed JSON, unknown review IDs, altered quotes, invalid signal types, duplicates, omissions, unsupported claims, and generic fallback labels, causing retry/split rather than customer projection. The server derives immutable offsets only from an unambiguous exact quotation.

Prompt/schema `semantic-taxonomy-v2-v22` / `cluster-interpretation-v9` ask for exactly one controlled semantic type, independent sentiment, bounded topic/label, and exact evidence for every fixed review ID. An explicit request for a capability or visible result is desired outcome even when the same comment explains the current failure that motivates it. Describing concrete workflow friction as frustrating remains pain unless the customer explicitly reports their own affect as the main signal; after ruling out an adoption or commitment objection, that first-person affect takes emotion priority. Labels and topics must name the concrete product, feature, workflow, or action in the evidence plus its concern or outcome; a generic consequence cannot stand alone. Achieved-value praise maps to desired outcome with positive sentiment; generic affective praise maps to emotion with positive sentiment. The server validates the versioned allowlist before persisting `canonicalOutcome`. After completeness, category-bounded candidate generation uses immutable source text and pinned source-text embeddings; exact normalized duplicates are direct edges and every other eligible pair requires adjudication. Generated topic, label, aspect, and evidence are payload for meaning and grounding, never planner eligibility. A raw-eligible connected component with at most 16 complete pairs retains every qualifying candidate; larger components retain only pairs whose endpoints rank each other in their stable top four eligible neighbors by similarity then pair ID. When one trigger connects two deterministic components, the planner adds the complete component cross-pair set only when it contains at most 16 pairs, so the existing complete-link gate can adjudicate every required edge. A true adjudication requires naming one specific operator intervention that addresses both comments; if that intervention differs for either comment, the decision is false. Only those fixed pairs may receive a same-actionable-topic adjudication; the response cannot add members, counts, rank, readiness, or publication state. Deterministic complete-link compatibility prevents an accepted pair from creating broad transitive membership. Failed, rejected, or over-limit component pairs remain separate emerging signals.

The public temporary demo does not fork this pipeline. After the shared CSV alias/mapping/row preflight and isolated import persistence, it calls the same `processAnalysisRun` entry point, durable categorization worker, and selective pair-adjudication seam as the authenticated path. Up to the remaining 50-comment allowance may be accepted from one or more CSVs; interpretation still uses normal five-comment categorization batches. Missing/invalid individual categorization after recovery fails the demo. Pair adjudication is optional for completeness: an unavailable or invalid decision leaves the pair separate. Public projections use neutral analysis-engine language.

### Compatible project semantic reuse

Every analysis request still creates a new immutable run and freezes its full current review inventory. When migration 008 is available, the runtime may reuse a project embedding, per-review canonical outcome, or canonical fixed-pair boolean only under the exact recorded contract: pipeline, preprocessing, embedding model/version, interpretation prompt/schema/model, candidate-planner version, and routing policy. Normalized content hashes bind embeddings and review outcomes; canonical ordered review IDs bind pair decisions. Every prior included review in the selected compatible base run must have an unchanged complete decision. One missing review, changed hash, version mismatch, absent table, or invalid lineage fails closed to the ordinary full path. Newly appended reviews and newly generated canonical pair IDs alone enter model work. Final grouping always reruns the existing candidate planner and complete-link projection across the new run; cached vectors and pair booleans cannot create membership on their own.

The feature-gated aspect candidate uses the same immutable-run rule but makes every extracted exact signal span independently addressable. Its canonical aspect key and fingerprint bind review content, controlled signal type, quote text, and source offsets; mutable corpus-derived aspect/topic labels are excluded. The separate full semantic contract binds pipeline, preprocessing, embedding, prompt, schema, model, candidate, and routing versions, and a run-scoped link maps a compatible stored decision to the fresh signal ID. Reuse requires complete unchanged prior aspect lineage under that contract. Exact canonical signal-type/aspect identity remains only a grouping rule after interpretation; it is not reuse identity. Text-identical work within one review is interpreted once, including failed-batch recovery, then fanned back out to every original span so evidence, provenance, counts, and Curation stay occurrence-exact. If the flag, tables, or compatible lineage are absent, processing takes the established review-level full path.

At larger scale, 1,000 valid comments use 200 normal categorization calls. One failed five-item batch recovered by its `2/3` children adds two calls, making 202 total. A complete split tree to singletons is nine calls for that original batch, making 208 total if it is the only failed batch. All 200 batches reaching singleton leaves is 1,800 categorization calls and an operational alarm. Selective pair adjudication is additional: the deterministic planner retains all qualifying edges only inside raw-eligible connected components of at most 16 complete pairs, otherwise retains only mutual stable top-four eligible neighbors, expands a triggered deterministic-component cross-product only up to 16 pairs, and batches five pairs per call instead of issuing blanket pairwise comparisons.

The same task contract is provider-independent. A local OpenAI-compatible `llama.cpp` server may be evaluated as a fallback using an official sub-500 MB GGUF artifact. Initial benchmark candidates are `HuggingFaceTB/SmolLM2-360M-Instruct-GGUF` Q8_0 (386 MB) and `Qwen/Qwen2.5-0.5B-Instruct-GGUF` Q4_K_M. Neither is approved until it passes the 100-record food fixture, exact-span and unsupported-claim gates, CPU/RAM limits, and analyst comparison.

## Current implementation

Phases 1–10 are implemented as `semantic-voice-map-v5` with `deterministic-preprocessing-v1`, `semantic-cluster-pipeline-v4`, `mutual-knn-cluster-v1`, pinned `Xenova/multilingual-e5-small` q8 ONNX embeddings, pinned `Xenova/distilbert-base-multilingual-cased-sentiments-student` q8 segment sentiment, and the default configured `llm-interpreted-theme-engine-v1` presentation engine. `deterministic-theme-engine-v2` remains the explicit degraded fallback. Current local runs no longer call the historical keyword or adaptive-frequency extractors. Positive, neutral, and negative sentiment remain orthogonal diagnostic metadata; they do not form semantic taxonomy values or recurrence states. After complete per-comment interpretation, the server transactionally replaces provisional themes with taxonomy-v2-bounded recurring projection candidates; unmatched comments project as emerging. Exact segment offsets, model and clustering versions, parameters, diagnostics, full original text, and curation decisions remain traceable.

The provider-independent hybrid candidate validator is implemented as `hybrid-candidate-validator-v1`. It treats every model envelope as untrusted, binds it to the trusted organization/project/run and immutable review membership, enforces a type-specific allowlisted taxonomy and payload limits, and accepts only exact original-text evidence. Incorrect offsets are repaired only when the exact quote occurs once; missing or ambiguous quotes are rejected. Accepted candidates remain separate proposals and never mutate deterministic artifacts.

The durable queue and bounded worker runtime are implemented behind injected provider, clock, jitter, governed-work resolver, candidate-acceptance, and price boundaries. The runtime handles lease/start/call/complete, optional verified or conservative spend reconciliation, zero-reservation capacity-priced dispatch, safe `Retry-After`, capped jitter, non-retryable failures, deadlines, disabled providers, retry exhaustion, and provider/model circuits with one half-open probe. Operational events contain only job/provider/model identifiers and sanitized dispositions. Bluerose configures the evaluated provider/model and capacity policy on the API-attached poller; `deployment-evidence/2026-07-14-bluerose-llm.md` records a live run with three successful jobs and two accepted OpenCode-backed themes. An independent continuously running worker, production policy, and production comparative evidence remain release work.
