# Security and Operations

Status: Baseline
Last updated: 2026-08-13

## Data protection

- Enforce organization/project isolation in application authorization and forced PostgreSQL RLS for every tenant-owned table.
- Encrypt OAuth refresh tokens and API credentials with envelope encryption; separate key management from the database.
- Request the minimum viable provider scope and keep the product read-only until write features are explicitly designed.
- Never expose tokens to the browser after callback completion or log credential payloads.
- Minimize reviewer PII; retain display identity/profile links only when necessary and policy-permitted.
- Support retention periods, project deletion, credential revocation, and deletion verification.

The unauthenticated waitlist write boundary stores only name, normalized email, consent version, and server timestamp. Input is bounded and validated, duplicate email is idempotent, request bodies are not logged, and no public listing route exists. It creates no auth user, organization, membership, or session. Private monitoring is an application API only: the verified JWT email must equal the provisioned profile email and match the normalized server-only `VOICE_LAB_ADMIN_EMAILS` allowlist. `user_metadata` is never an authorization input, the claim email is not serialized by `/api/auth/me`, and direct `anon`/`authenticated` Data API reads remain revoked. Migration 005 is applied; production must define retention/deletion operations plus anti-abuse controls before promotional collection begins.

## OAuth protections

Use Authorization Code + PKCE, exact redirect allowlists, signed/expiring state bound to user/project/provider, nonce where applicable, refresh-token rotation handling, and explicit reconnect/revoke states. The test result distinguishes authentication, identity, entities, full-text review access, pagination, and refresh.

The local source now uses Supabase Auth as the configured email/password credential and session issuer. The browser receives only a project URL and publishable key; no service/secret key or password enters Voice Lab storage. The API verifies bearer claims and sets the verified `sub` as transaction-local RLS identity. On first login it may create only that subject's profile, exact `Personal workspace`, self-owner membership, `Default project`, and binding; repeat login is idempotent, user metadata never grants authorization, and unauthenticated requests never provision. Migration 007 grants this narrow insert path only to `voice_lab_api`; direct Data API roles remain denied. Account recovery, SMTP, and session-removal proof remain release gates.

The email-only local session-recovery endpoint accepts only loopback connections when `NODE_ENV` is not `production`; production receives the same 404 as an absent route. It is API-only, is never called or rendered by the public client, and must never be enabled as an internet-facing login mechanism.

The legacy staging credential is local QA compatibility only. The browser requires `VITE_LOCAL_QA_AUTH_ENABLED=true`; the API rejects the route in production mode even if old staging variables remain present. Supabase email/password is the only configured production login path.

## Import and model safety

Treat every CSV field as untrusted content. The server, not the browser, enforces CSV-only media/original-byte consistency, project/tenant authorization, request size, 10,000-row/100-column/10,000-character cell and comment limits, allowlisted mappings, rating/date validation, and HTTPS-only imported source URLs; loopback HTTP requires an explicit non-production flag. Arbitrary manual-comment, JSON, and workbook requests are rejected before queue creation. Stored review markup remains immutable literal data, React renders it as text, legacy unsafe source links are suppressed, and the PDF renderer escapes paragraph markup. There is no customer CSV export in the current product, so spreadsheet-formula injection has no outbound CSV surface; add formula neutralization before any such export ships. Current upload bytes are database-backed: private Storage policies/adapters exist but are not yet the live import path, and MIME/content/malware validation remains required before that cutover.

Public Demo admission hashes the resolved client address without storing the address, trusts forwarded headers only behind the explicit production proxy flag, and applies per-client hourly/active plus global active-run caps in the temporary Demo database. Authenticated import and analysis creation share one advisory-lock transaction and a small per-organization active-job cap. Both return stable `429` product errors without provider, database, or raw-input details.

OpenCode Go receives only the minimum review fields required for an approved task. Per-comment categorization receives fixed review IDs and review text; selective pair adjudication receives fixed pair/review IDs plus canonical topic, label, and exact quote only. Neither contract includes tenant controls, counts, ranking, readiness, source credentials, reviewer names, profile URLs, owner replies, or unrelated metadata. Provider terms, processing location, retention, and training-use controls remain release gates; secrets stay server-side and are redacted from errors, telemetry, dead-letter payloads, exports, and support tooling.

Each categorization prompt contains a bounded batch and minimum immutable text for one taxonomy-v2 signal per comment. The server validates identity, completeness, the versioned semantic allowlist, orthogonal sentiment allowlist, exact evidence, and non-generic label quality. It does not use keyword cues to override an allowed model category; semantic repeatability is measured in controlled and held-out evaluation. Category/topic overlap is mandatory for recurrence; sentiment never changes semantic category or recurrence. A one-token two-comment pair additionally needs local normalized `aspect + label` cosine `>= 0.90`; a one-token edge in a 3+ component needs cosine `>= 0.88`. Cosine cannot create a no-overlap merge or remove customer visibility. No grouped customer payload is sent through a second model call. Local endpoints retain the same payload, model, no-tools, and network controls.

Model calls have no tools, network callbacks, or authority to mutate reviews, themes, curation, reports, budgets, or credentials. Treat all output as untrusted candidate data. Enforce output-schema size/depth limits, exact evidence spans, tenant/run ownership, taxonomy allowlists, and unsupported-claim rejection before persistence.

Overview intelligence is a read-only synthesis call after run authorization. Its prompt excludes reviewer PII, source URLs, tenant controls, counts, rank, and credentials; public responses exclude provider/model identity. The parser accepts only bounded prose and existing effective-theme IDs. Failure or invalid citations expose deterministic proof only and cannot mutate the saved map, Curation ledger, report, or evidence.

The local ONNX embedding model is non-generative and cannot become an evidence authority. Pin its artifact revision/dtype, verify cache integrity at deployment, prohibit arbitrary per-request model IDs or URLs, bound segment length/batch size/runtime memory, and keep model-cache writes outside tenant-controlled paths. Customer text remains data and the only evidence is the immutable review plus validated offsets.

Queue authorization is tenant-scoped. Request/token buckets plus global, provider/model, and organization concurrency are mandatory deployment control-plane policy. Monetary budgets are a separate opt-in policy: only privileged administrators may request organization/project limits, and analysis workers may reserve and reconcile but may not increase them. Integer-micro reservations and append-only usage/audit events prevent floating-point drift when spend enforcement is enabled; zero-reservation capacity-priced jobs never write fake monetary ledger entries.

## Operations

Monitor sync success, provider latency/rate limits, queue depth, stage duration, retries, analysis cost, unsupported-claim evaluation, and report generation. Define alerts for stuck jobs, token-refresh spikes, tenant-isolation failures, and provider contract drift.

For LLM work, the production observability gate is to monitor queue depth/age by tenant and task kind, active/expired leases, request/token bucket saturation, budget reservations versus reconciled cost, retry and dead-letter rates, circuit state, fallback rate, schema rejection, exact-span rejection, and unsupported-claim rate. Alert on sustained oldest-job age, repeated lease expiry, ledger imbalance, budget overrun, provider authentication failures, circuit-open duration, and any secret/PII detection in logs. Queue state and sanitized worker events exist locally, but no production metrics exporter or alert proof is implemented yet; do not treat logs or the browser progress projection as operational saturation monitoring.

Rate control is dual-dimensional per provider/model: request capacity and estimated/observed token capacity, plus global and per-organization concurrency ceilings. Respect `Retry-After` delta seconds or HTTP dates. Backoff is capped exponential with full jitter and a configured maximum attempt count. Dead-letter records retain sanitized classification and hashes, never raw prompt/customer text.

Circuit breakers open per provider/model after a configured consecutive/transient failure threshold, reject dispatch during the cool-down period, and permit a bounded half-open probe. Provider outage, open circuit, deadline expiry, retry exhaustion, or an explicitly enabled verified-price budget must terminate in a recorded degraded mode rather than masquerade as complete model analysis.

The implemented circuit record persists `closed`, `open`, or `half_open`, a consecutive-failure count, threshold, cool-down deadline, and a single half-open in-flight claim. `429` responses respect quota scheduling but do not count as provider-outage circuit failures. Transport/eligible provider failures do; authentication and missing-model failures are non-retryable. Provider health, rate buckets, and concurrency limits are deployment control-plane tables, revoked from `PUBLIC`, and are not exposed through tenant APIs. Queue admission locks these policy rows and counts unexpired active leases before quota debit, preventing concurrent workers from bypassing caps or consuming tokens for work that cannot dispatch.

Usage and audit events record organization, project, run, task kind, routing-policy/prompt/schema versions, provider/model identifiers, timestamps, reserved/reconciled integer micros, request/token counts, result disposition, and sanitized failure class. They never record credentials, raw review text, reviewer PII, full prompts, or hidden model reasoning.

The local API defaults request bodies to 5 MiB, marks JSON responses `no-store` and `nosniff`, marks PDFs private/no-store, and avoids logging raw exception messages. When cookie authentication is used with `GARAXE_ALLOWED_ORIGIN`, state-changing requests must match that exact origin. Distributed rate limits, edge CSP, durable audit logging, and managed observability remain deployment gates.

The Bluerose staging origin uses only ClusterIP services. Cloudflare Tunnel is the sole public path, and the route must be appended without altering Portfolio or the terminal 404 fallback. Namespace default-deny policy permits Cloudflare-to-web, web-to-API, API/migration-to-PostgreSQL, required DNS, and API-to-public-IPv4 TCP 443 for the authorized OpenCode Go adapter. Private, local, test, and reserved networks are excluded from that HTTPS rule. Standard Kubernetes NetworkPolicy cannot restrict by provider FQDN, so the fixed server-owned provider URL and absence of user-controlled destinations are compensating staging controls; production requires domain-aware egress enforcement. Google credentials remain absent and Google live use remains gated.

The 2026-07-14 rollout followed that order: Cloudflare configuration version 46 preserved Portfolio and the terminal 404, then added Garaxe; the new proxied CNAME and authenticated public traversal were re-read and verified. See `deployment-evidence/2026-07-14-bluerose-staging.md`. This evidence does not replace managed edge policy, monitoring, or incident-response gates.

## Current local persistence boundary

Migration 001 enables and forces RLS on all 22 tenant-owned tables.

Local Supabase staging and production are separate trust domains. Local uses only CLI-generated loopback values in the ignored `.env`; production values remain in Kubernetes ConfigMaps/server-only Secrets. `npm run test:e2e:local-supabase-auth` refuses non-loopback targets. After proof, `npx supabase stop --project-id voice-lab-local --no-backup` removes containers, network, and test volumes while preserving source/config.

PGlite is used only as the local MVP database adapter. It is excluded from Git under `.local/`, creates its parent directory explicitly, and uses parameterized queries for user values. `DATABASE_URL` selects node-postgres only for authenticated persistence; Demo uses a separate `GARAXE_DEMO_DB_DIR` PGlite handle and cannot enter the managed database accidentally. Both handles receive the shared queue worker, while startup and one-minute expiry cleanup target Demo only. Managed PostgreSQL startup performs no DDL. Managed bootstrap is migration-file-only through 007. Migration 001 forces tenant RLS; 003 protects artifact metadata; 004 hardens server-only tables and helper execution; 005 narrows waitlist monitoring; 006 defines the non-bypass runtime login; and 007 permits only that API identity to insert a verified subject's exact personal onboarding records. `auth_sessions` and `demo_analysis_sessions` remain inaccessible to the managed API role, direct `anon`/`authenticated` inserts remain revoked, and Demo never enters this database. Private Storage calls use a publishable key and the current user's JWT, never a service key. Production still requires distributed rate limiting, structured audit logging, backup policy, and a durable external job runner.

Bluerose staging uses a pinned PostgreSQL 16 image and a retained 50 GiB host-backed volume on the single node. Because the static hostPath provisioner creates a root-owned volume directory, a one-shot init container creates only the exact `pgdata` subdirectory with UID/GID 999; that init step runs as root with only `CHOWN` added after dropping all capabilities, while the long-running PostgreSQL container remains non-root. The in-cluster hop explicitly disables PostgreSQL TLS only while NetworkPolicy confines it to the namespace. External or paid-beta PostgreSQL defaults to certificate verification and may load a private CA bundle. The deployment rehearsal produced a custom-format dump, restored it into a disposable database with matching bounded counts, and copied it off Bluerose. That one-time staging artifact is not a managed backup policy, and the single-node volume is neither managed storage nor disaster recovery.

## Current PDF rendering boundary

The local API passes only a server-owned immutable snapshot to a fixed renderer script and never accepts a command, script path, output path, or template from the browser. The subprocess is replaceable infrastructure, not a public execution surface. Production should run it in a resource-limited worker with bounded snapshot size, timeouts, isolated temporary storage, dependency pinning, and redacted failure logs. A downloaded PDF inherits the report's reviewer-data retention and access-control requirements.

The staging API image pins ReportLab, runs as a non-root user with a read-only root filesystem, and provides only a size-limited temporary volume. PDF isolation into an external durable worker remains a paid-beta requirement.

The public demo is a bounded exception to report authentication, not an anonymous workspace. It accepts only mapped CSV within 16 KB; the initial file contains 6–10 comments and later token-scoped files 1–50. One temporary project accepts 50 unique comments, then rejects uploads for eight hours from exhaustion; duplicate retries neither consume capacity nor create a run. It accepts no path, provider, model, destination, Google credential, team identifier, or provider credential. Starts are globally capped at 20 per rolling hour, each high-entropy token resolves to one isolated tenant/project and current immutable run, and complete exact-span-validated individual categorization is required before exposing evidence or a PDF. Bounded fixed-pair adjudication may follow through the same queue but cannot change completeness, access, counts, or projection. Unresolved pairs remain emerging. Token-scoped Curation cannot address authenticated runs. Public result, curation, error, status, and PDF projections use neutral product/source language rather than provider identity. The server stores only the token digest. Provider credentials remain server-side and are never returned or logged.

Demo source and derived data use a fixed 24-hour expiry set at creation, not sliding activity. Startup cleanup plus a one-minute sweep deletes expired projects and organizations, with database cascades covering import payloads, reviews, analysis artifacts, queue jobs, demo sessions, curation sessions, and curation actions. PDF generation creates no Reports or download-history row, labels output as a demo, sends explicit no-store/no-cache headers, and deletes the unique temporary output after reading it. Browser-downloaded copies are user-controlled. Authenticated `/api/reports/:id/pdf` behavior is unchanged.

## Provider/legal boundary

The MVP uses customer-authorized connections and uploads. Provider terms, storage/retention rights, reviewer display requirements, and data-processing roles require legal review before production launch. No arbitrary scraping or redistribution is authorized by these specifications.
